# 决策模型四方评测 · 项目与结果说明

> 本文沿用原架构叙述，**结果部分已更新为 PubMedQA 大样本运行**
> （500 题 × 3 轮 × 4 家 = 6000 次正式请求，运行目录 `results/20261012T124545_166990Z`）。
> 此前 12 题演示集的结论作为「流程验证阶段」保留在第五节，不再作为主结论。

---

## 一、项目构建与架构

项目构建从一个能够调用百炼接口的 Python 示例开始，先验证认证、请求格式和返回结果，再逐步扩展成统一的评测框架。微软 Decision-1、Qwen3.5-9B 和 Jev 通过 OpenRouter 接入，百炼使用自己的决策接口；各服务的差异由适配层处理，数据加载、任务调度、结果评分和报告输出则共用一套逻辑。

专用决策接口直接接收业务状态与问题定义，Qwen 则通过严格的 JSON Schema 返回相同的类别键，并固定关闭思考、使用指定上游和 BF16 配置。这样做既减少了自由文本解析带来的干扰，也保留了真实服务之间的接口差异。

整个项目目前通过 **34 项离线测试**（框架从三方扩展到四方时新增了 Jev 适配与四方配对统计的用例），实际运行会保存请求内容、原始响应、模型版本和上游信息，方便后续定位问题与复核结论。

**接入方式一览**

| 服务 | 入口 | 协议 |
|---|---|---|
| 阿里云百炼 | 自有决策接口（国内直连 systemone） | decision |
| 微软 Decision-1 | OpenRouter `/api/alpha/decisions` | decision |
| TypeSafe Jev 1.13 | OpenRouter `/api/alpha/decisions` | decision |
| Qwen3.5-9B | OpenRouter `/api/v1/chat/completions` | chat + 严格 JSON Schema |

微软、Qwen、Jev 三家共用同一把 OpenRouter 密钥，百炼单独使用自己的密钥。

## 二、测试设计

测试设计首先服务于可复现性。

**流程验证阶段**使用 12 道人工示例（物理、化学、生物各 4 道），要求模型仅根据给出的记录，将结论判断为「支持」「反驳」或「信息不足」，题目覆盖数值关系、实验条件、测量缺失以及证据与结论不匹配等情况。这批数据的作用是验证链路是否打通，样本量不足以支撑选型判断。

**主评测阶段**改用 PubMedQA 的专家标注数据：从作者仓库下载 1000 条 PQA-L，按标签分层、固定随机种子划分为 dev 199 / test 801，再从 test 中按种子抽样 500 题。题目要求模型仅依据提供的摘要上下文，将研究问题判断为 `yes` / `no` / `maybe`。导入时只把研究问题与摘要正文放入请求，排除 LONG_ANSWER，**标准答案只保存在本地，不进入任何模型请求**；数据来源与文件哈希记录在 `provenance.json`。

四家服务在同一次运行中处理相同题目，每题重复三轮，并随机安排调用顺序；每家先完成 10 次暖机，随后产生 1500 次正式请求，四家合计 6000 次。准确率只统计首轮的 500 个独立输入，重复轮次用于观察响应耗时和输出一致性，避免把同一道题重复调用三次包装成三倍样本量。

计时从客户端发出 HTTP 请求前开始，到完整响应体接收结束，测量的是用户实际经历的服务等待时间。

## 三、项目功能

项目功能围绕「答得对不对、返回得快不快、结果是否值得信任」展开。

准确率和 Macro-F1 用于衡量分类表现，混淆矩阵和分类别指标帮助区分错误类型，P50 与 P95 分别反映典型等待水平和较慢端的响应情况，失败率与重复一致性则补充说明服务运行状态。在大样本规模下，框架还给出**按样本 ID 聚类的配对 bootstrap 区间**，用于判断两家之间的差距是否超出抽样波动——这是小样本阶段无法回答的问题。

对于实际返回类别概率的决策模型，框架计算 Brier 分数和 ECE，观察概率与正确性之间的关系，并绘制覆盖率—准确率风险曲线用于选定自动处理阈值；Qwen 本次只被要求返回类别，因此相关概率指标标为不可用，**不用自报置信度或人为构造的分布填补空缺**。

运行结果可以在 HTML 报告中查看，本次实测另整理成包含八张图示的 14 页 PDF，首页直接呈现结论，并用浅绿色标记各项最优结果。

## 四、主结果：PubMedQA 大样本实测

本轮 6000 次正式请求中，**5986 次成功**。百炼、微软、Jev 三家零失败；Qwen 出现 14 次失败，全部为 OpenRouter 共享池上游限流（HTTP 429，`engine_overloaded`），属可用性问题而非模型能力问题，但提示依赖共享池路由的服务在批量负载下存在限流风险。

**准确率与分类表现**

| 服务 | 首轮正确数 | 准确率 | 95% Wilson 区间 | Macro-F1 |
|---|---|---|---|---|
| Jev 1.13 | 390 / 500 | **78.00%** | [74.16%, 81.41%] | **0.6430** |
| 微软 Decision-1 | 376 / 500 | 75.20% | [71.23%, 78.78%] | 0.6042 |
| Qwen3.5-9B | 337 / 500 | 67.40% | [63.17%, 71.36%] | 0.5716 |
| 阿里云百炼 | 322 / 500 | 64.40% | [60.11%, 68.47%] | 0.4841 |

**这一轮的关键变化是差距首次可判定**：六组两两配对中有四组的 95% 区间不含零。Jev 与微软分别显著优于百炼（+13.60pp、+10.80pp）和 Qwen（+10.60pp、+7.80pp）；而 **Jev 与微软之间相差 2.80pp、区间 [−6.20, +0.60] 含零，两者统计等效**，不能宣称其中任一方更准。百炼与 Qwen 之间同样不显著。

**响应速度呈现了另一种排序**：百炼 P50 约为 121.1 毫秒，Jev 为 497.9 毫秒，微软为 525.9 毫秒，Qwen 为 1012.7 毫秒。百炼的 P50 比 Jev 低约 75.7%，并以 100% 的重复一致率完成全部判断。需要注意，百炼走国内直连而其余三家经 OpenRouter 跨境路由，这一差距包含网络路径差异，不能等同于模型本身更快。

**概率质量**

| 服务 | Brier（越低越好） | ECE | 有效概率 |
|---|---|---|---|
| Jev 1.13 | **0.3366** | 0.1181 | 500 / 500 |
| 微软 Decision-1 | 0.3553 | **0.1058** | 500 / 500 |
| 阿里云百炼 | 0.5139 | 0.1700 | 500 / 500 |
| Qwen3.5-9B | 不可用 | 不可用 | 0 / 500 |

Jev 的 Brier 最低、微软的 ECE 最低，两者校准质量接近；百炼两项指标均明显偏高，其置信度可靠性较弱。

## 五、错误结构比总分更有解释力

大样本让错误类型的差异暴露得更清楚，这比总分更能指导选型。

**四家在 `maybe`（证据不足）类上集体失效**：F1 分别为百炼 0.141、微软 0.187、Qwen 0.211、Jev 0.236，**全部低于 0.24**。混淆矩阵显示 `maybe` 行几乎没有被正确命中，多数被判成 `yes` 或 `no`——模型倾向给出明确结论，而不愿输出「不确定」。这是决策模型品类的共性短板，不是某一家的缺陷。其直接含义是：**凡涉及「证据是否充分」的判断，都不应交给模型自动裁决，必须人工复核或规则兜底。**

**百炼存在结构性偏向**：其 `no` 类召回仅 33.7%，即大量「反驳」被判成「支持」，这也是它 Macro-F1 最低（0.4841）的主因。在需要识别否定结论的场景中，这一偏向的风险远大于准确率数字本身所反映的程度。作为对照，Jev 的 `no` 召回为 82.6%，微软为 77.0%，Qwen 为 64.0%。

百炼与 Qwen 的总体准确率仅差 3.00 个百分点（区间 [−7.20, +1.20] 含零，不显著），但两者的错误结构完全不同：百炼偏向把否定判成肯定，Qwen 则在证据缺失时倾向给出反驳。**总分接近不代表可以互换使用。**

在流程验证阶段的 12 题上也观察到了同向的线索：百炼错在一道明确的数值比较，Qwen 把「没有测量相关指标」判断成了「结论被反驳」。大样本结果说明这两类错误不是偶发个例，而是可重复的倾向。

## 六、从结果到选型

阈值在**独立 dev 集（100 题）选定为 0.90**，再到 test 验证，未用 test 成绩反推。迁移偏差仅 0.2–4.6 个百分点，说明该阈值可直接用于生产配置。

| 场景 | 推荐 | 依据 |
|---|---|---|
| 准确率优先 | Jev 或微软 | 78.0% / 75.2%，显著优于另两家；二者间无显著差异 |
| 追求最少人工 | **Jev** | 阈值 0.90 下自动处理 70.2%，人工量仅 29.8% |
| 自动错误代价高 | **微软** | 自动子集准确率 90.7%，自动集错误数最低（26 个） |
| 毫秒级实时链路 | **百炼** | P50 121 毫秒、重复一致率 100%；须接受准确率落后约 11–14pp |
| 不建议做生产决策 | Qwen3.5-9B | 延迟最高、无原生概率，且遇上游共享池限流 |

推荐部署形态：Jev 或微软作主决策 + 置信度 0.90 分流 + `maybe` 类与低置信统一转人工；百炼可作延迟敏感场景的前置粗筛，但需叠加否定结论的规则校验。

模型选择需要结合具体错误成本——准确率、校准质量、速度优势和错误偏向都应该在真实任务中分别验证。

## 七、本次仍不能外推的部分

- **PubMedQA 是公开数据集**，题目可能已进入各模型训练数据，绝对准确率可能偏高；跨模型的相对比较受影响较小，但结论仍应以新收集并独立标注的样本复核。
- **延迟不可直接跨家比较**：百炼国内直连，其余三家经 OpenRouter 跨境路由。
- 仅测试 choice 三分类，未覆盖 Score / Noul 题型、长文档（本次输入字符数 p50 约 1868）、高并发（本次并发 1）、跨时段稳定性与计费一致性。
- 六组配对未做多重比较校正，属探索性分析；`maybe` 类仅 50 例，其 F1 区间很宽。
- 各厂商公布的自测指标仍缺独立第三方验证，本文只以本次实测为准，不作为厂商能力的最终排名。
